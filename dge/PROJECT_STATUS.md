## Non-negotiable conventions (unchanged from project start)
1. Cache-busting via `?v=VERSION` on every script/link tag, bumped on every delivery that touches any file. `index.html` itself is not cache-busted — but it stamps its own version (`<meta name="dge-html-version">`) which `core.js`'s `DGE_EXPECTED_HTML_VERSION` checks against; **bump both together** on any change to `index.html`'s structure, or a stale-cached tab will show a "cached page, tap to reload" banner (or worse, silently misbehave if it predates that mechanism).
2. Zip delivery: only changed/new files, inside a `dge/` folder structure. **Known failure mode, now observed for real (see below): a zip built from a stale local checkout silently reverts whatever changed since that checkout was made, even in files it didn't mean to touch.** Always diff a synced zip against what was live immediately before syncing it, not just against what the zip's author intended.
3. Pre-delivery checks: `node -c` syntax, duplicate top-level identifier scan, HTML div balance, CSS brace balance, dangling reference check.
4. BYOK everywhere: GitHub PAT, Vision/Gemini keys all live in the user's own `localStorage`, never hardcoded, never sent anywhere but directly to the relevant API from the user's own browser.
5. **Licensing: absence of a licence is not permission** — copyright is automatic in essentially every country; an explicit grant is what makes reuse allowed. This project layers one additional rule on top: **the project lead can authorize a specific source for a specific, narrow use on a case-by-case basis**, given DGE's non-commercial/educational nature — this has actually happened (sri-aurobindo.co.in, numeric Ashtaka-mapping data only; several "Unclear"-licensed Kosha dictionaries and Ashtadhyayi commentaries, see their own sections below). What this project does **not** do: treat "no licence" as blanket permission, or treat non-commercial purpose as void-ing an explicit licence's stated terms, as a *general, standing* rule — every use of an unlicensed/ambiguous source is a specific, logged decision, not a default.

## Library Manager + content-ingestion pipeline (9 Aug 2026)

A parallel Cowork session delivered two zips: a **Library Manager** admin dashboard and a **GitHub Actions ingestion pipeline** with importers for 12 "clean, no-OCR" texts identified in its own sourcing report. Both are now integrated, but not as delivered — reviewing the actual code against the real catalog surfaced three real bugs, one of them a genuine blocker.

### 1. Library Manager (`dge/library-admin.html`)
Super-admin dashboard (passkey `SHRI108`, same as the rest of the admin surface) — overall load progress, per-section bars, a searchable/filterable taxonomy tree, and a show/hide tool that exports `library-visibility.json`. Reachable from the 🛡️ Admin menu → **🗂️ Library Manager**.
- **Wired the show/hide hook into the public library** (`js/library.js`'s `openLibraryModal()`), which the incoming README explicitly offered but didn't build: hiding a node now actually excludes it (and its subtree) from what the main reader app shows, once `library-visibility.json` is committed to `dge/data/`.
- **Fixed a real counting bug in `tools/gen_library_status.py`** before it ever ran against real data: the delivered script derived each leaf's file location purely from `taxonomy.json`, guessing `<leaf>/data.json`. That's wrong for every leaf that nests a nested layer folder under itself — which turns out to be a real, load-bearing, already-in-production convention (all of Sarvamoola's actual live content, most monolithic Purāṇas, and every individual Rāmāyaṇa/Mahābhārata kāṇḍa/parva use a `mula/` subfolder, leaving room for a future sibling commentary layer). The delivered script would have silently kept reporting these leaves as empty forever, even after the new ingestion pipeline below writes real content into them. Fixed by cross-referencing `data/library.json` (the one place a leaf's real path is already correct, mula-nested or not) instead of re-deriving it, and by counting actual verses instead of chapter-count for the newer nested-item schema. Verified against the live repo (reproduces the exact 94/556/54,959 ground truth) and against a simulated write into a `mula/`-nested leaf (correctly picks it up; the original script does not).

### 2. GitHub Actions ingestion pipeline (`.github/workflows/ingest.yml`, `importers/`)
Manually-triggered (`workflow_dispatch`) workflow: pick a text from a dropdown → runs the matching Python importer (fetches from GRETIL / sanskritdocuments.org / bombay.indology.info's BORI critical editions — all long-established, purpose-built academic Sanskrit e-text sources, IAST/ITRANS→Devanagari via `indic_transliteration`) → writes `data.json` → opens a PR for review before merge. Nothing auto-commits to `main`.
- **Covers, this batch:** Śrīmad Bhāgavata (12 skandhas), Vālmīki Rāmāyaṇa (7 kāṇḍas), Mahābhārata (18 parvas), Harivaṃśa, 6 smṛtis (added Nārada; Manu/Yājñavalkya/Parāśara/Gautama/Viṣṇu already existed), and 4 kāvyas (Raghuvaṃśa, Kumārasambhava, Kirātārjunīya, Śiśupālavadha) under a **new `kavya` top-level taxonomy section**.
- **Reviewed every line of the incoming code before wiring it in** (it runs in CI with `contents:write`/`pull-requests:write`) — no `eval`/dynamic imports, fixed hardcoded source URLs only, standard well-known `peter-evans/create-pull-request` action. Hardened the one style nit: the workflow's `text` dropdown choice now passes through an `env:` var instead of being interpolated directly into the `run:` shell line.
- **Fixed a real naming mismatch**: the importer's own Mahābhārata parva-name table called book 3 "aranyaka"; the catalog already has it scaffolded as "vana" (traditional alternate name for the same parva) — would have written real content to a path nothing in the taxonomy points at, silently invisible. Fixed to match the existing catalog.
- **Fixed target paths for Rāmāyaṇa/Mahābhārata/Harivaṃśa/the 4 new kāvyas** to include the `/mula` layer segment (see above) — the delivered importers targeted the flat, un-nested path for these, which is a dead placeholder file for these specific leaves, not what `library.json`/the reader app actually fetches. Bhāgavata and the smṛtis were already correctly flat (matching their own existing catalog entries) and needed no change.
- **Found and fixed the actual blocker**: none of this schema (`itihasa_purana_text` — a chapter-level item carrying its own nested `shlokas[]` array) had ever been wired into the main reader app's data adapter (`dgeNormalizeGranthaData()` in `js/core.js`). The existing code only handled the flat, one-item-is-one-verse `vedic_text` shape; fed a nested-chapter file, it would have rendered every "verse" as blank (reading a non-existent `.sa` field off a chapter object). This is presumably *why* none of the 0-of-many `itihasa_purana_text`-schema catalog entries were populated yet, before today. Added the missing normalization branch — flattens chapters into the same sequential-integer-keyed shape every other module already assumes, carrying the chapter's reference (e.g. "Bāla Kāṇḍa, Sarga 3") through the existing generic `vedicId` extra field rather than wiring a new one through render/audio/filter. Verified both the new branch and the pre-existing `vedic_text` branch in a real browser, and ran a full importer→taxonomy→status-dashboard dry run end-to-end in an isolated scratch copy before touching real data.
- **New taxonomy leaves added**: `smritis/narada_smriti`, `itihasas/harivamsha`, and the new `kavya` section (`raghuvamsha`, `kumarasambhava`, `kiratarjuniya`, `shishupalavadha`) — each pre-scaffolded with an empty-`items` `data.json` and a `library.json` entry, ready for the importer to fill.

### Live run results (same day, after the above was built)
Ran all 13 texts for real once workflow permissions were enabled. 11 landed clean on the first or second try; 2 remain blocked. This is deliberately reported in full, mistakes included, since a pipeline's real trustworthiness only shows up in what actually happened when it ran, not the design intent.

- **Landed and verified rendering correctly in the live app**: Vālmīki Rāmāyaṇa (7 kāṇḍas), Mahābhārata (18 parvas), Śrīmad Bhāgavata (12 skandhas), Manu/Parāśara/Yājñavalkya/Nārada smṛtis, Raghuvaṃśa, Kumārasambhava, Kirātārjunīya, Śiśupālavadha.
- **Two more real bugs found by actually running it** (beyond the schema-adapter gap already described above), both fixed and re-verified before merging:
  - **GRETIL page-break artifact**: some GRETIL pages mark an original print-page break with a run of underscores glued directly onto the following word rather than sitting on its own line — hit nearly every chapter of Raghuvaṃśa (`"_______...___ agnivarNam..."`). Underscores never appear in real Sanskrit verse text, so any run of 3+ is now stripped in `gretil.py` regardless of position.
  - **ITX inline hyphenation marker**: a literal `\-` (LaTeX-style explicit-hyphenation-point marker some sanskritdocuments.org `.itx` sources keep inline) was splitting words apart — ~50% of Kirātārjunīya's verses, ~5% of Kumārasambhava's. Not caught by the existing "line starts with `\`" skip since it can sit mid-word. Now stripped explicitly in `itx.py` before transliteration.
  - Both confirmed via a full read-through verification pass across all 10 then-open PRs (not just spot-checks) before any were merged — this is what caught them; neither would have been visible from the CI job's own "success" status.
- **Still blocked, not merged — Harivaṃśa and Viṣṇu Smṛti**: both importer runs completed "successfully" but wrote 0 verses (confirmed in the job logs: `wrote ... (0 units, 0 shlokas)`). Their specific GRETIL source pages evidently use a structure the current regex-based parser can't match — Harivaṃśa's URL is a different, newer TEI-derived page pattern (`corpustei/transformations/html/...`) than the ones that worked; Viṣṇu Smṛti's URL looks like its working sibling smṛtis' but still yields nothing. Diagnosis needs the actual page HTML inspected directly, which this sandbox's network egress policy blocks (`gretil.sub.uni-goettingen.de` is not reachable from here). **Left undone, not silently marked complete** — no PR exists for either.
- **A fourth real bug, the most consequential one**: every importer correctly wrote its `data.json` and correctly updated the dashboard-only `library_status.json`, but **none of them ever flipped the actual catalog's `populated: true` flag** in `data/library.json` — which is the one thing `dgeNormalizeGranthaData()`'s caller in `core.js` actually gates on before even attempting a fetch (`entry.populated === false` short-circuits straight to "Not Yet Available"). All ~117K newly-ingested verses were technically on `main`, syntactically valid, and completely invisible to any user, until an end-to-end browser test against the live app (not just checking the JSON) caught it. Fixed by flipping `populated: true` (and adding a `title`, matching every other populated entry) for all 45 leaves ingested today. **This exact gap recurred a second time** the same day (Viṣṇu Smṛti's PR merged with real content but `populated` stayed `false` until another manual fix) — see "Round 2" below for the permanent fix.

Tested: confirmed idempotent against the current fully-synced state (no spurious changes), and confirmed it correctly detects and fixes a deliberately-unflipped flag in a synthetic before/after test. No future ingest should need this as a separate step again.

### Round 3 — Harivaṃśa actually solved (a third, correctly-diagnosed fix)
A third delivery (`HARIVAMSA_FIX.md` + `parse_harivamsa.py`) correctly identified what the first two rounds got wrong: **the blocker was never the sandbox's network access.** Harivaṃśa's GRETIL page uses a genuinely different marker convention from every other text in this corpus — a verse ends in a bare `// HV_c.v` (dot separator, no closing `//` — the reference itself terminates the marker) instead of the common `// ABBR_c.v //`, and a star/secondary-recension passage ends in `*HV_c.v*n` with `|` as its internal pada separator instead of `/`. No regex built for the common pattern could ever match either shape. The fix also switched the source URL from the `corpustei/transformations/html/...` export (a different, TEI-derived HTML structure entirely) to the **plaintext transformation** of the same constituted text, which is where this marker convention actually appears.

- **Reviewed and integrated, not applied verbatim**: adapted the incoming `parse_harivamsa.py` logic into a dedicated `_hv_parse()` path in `gretil.py`, dispatched only for `tid=="harivamsha"` — every other GRETIL entry is untouched. Verified against a synthetic sample reproducing the documented format (header rule, an interlocutor tag, an editorial commentary span, one star passage) before touching real data: all four cases handled correctly.
- **First real CI run**: 0 → 6,070 shlokas across 119 adhyayas — genuine progress, but **pulling and inspecting the actual generated file (not just trusting the CI job's "success" status) caught a second, real bug**: this specific plaintext page's own metadata header — plain English text ("Editorial lines: = header = commentary ## Revisions: ... TEI encoding by mass conversion of GRETIL's Sanskrit corpus") — carries no underscore-rule separator at all (unlike the older-style pages this project had seen before), so it fell through to a weaker fallback and got run through `iast_to_dev()` as if it were Sanskrit, landing as phonetic Devanagari garbage (`एदितोरिअल् लिनेस्...` = "Editorial lines...") prepended to the mangala verse.
- **Fixed by anchoring the strip on a literal `# text` marker** that this header reliably ends in (visible untouched in the corrupted output, since `x` isn't an IAST letter and passes through the transliterator unmapped). Verified against both the real corrupted header (now clean) and the original synthetic regression sample (unchanged) before re-running and merging (PR #23, `addcb33`).
- **Also found and fixed the same missing-`title` bug as Sarvamoola** (see above) for the newly-merged `itihasas/harivamsha/mula` entry — confirmed live in browser: heading reads हरिवंशः, mangala verse renders correctly, 6,070 shlokas, no JS errors.
- **One known, openly-documented limitation, not hidden**: Harivaṃśa's text opens with a substantial invocatory/benediction passage (praise of Vyāsa, Gaṇeśa, an unnamed further deity) that the source itself marks with **no per-verse reference at all** until a single `// HV_1.1` at its very end — roughly 20 real verses land as one merged entry rather than individually split, because there is no marker in the source to split on. The Sanskrit text itself is intact and correctly converted; it's simply coarser-grained in this one ~20-verse span than the rest of the text. Splitting it further would need either the raw page's actual paragraph/line structure (not available from this sandbox) or a heuristic (e.g. splitting on internal daṇḍa punctuation) that hasn't been verified against ground truth — left as a known, minor follow-up rather than guessed at.

- **A process mistake worth recording**: while resolving a cascading `git merge` conflict (every ingest branch regenerates the same shared `library_status.json` off the same stale base, so merging them one after another kept conflicting on that one generated file even though the real verse data never conflicted), an early fix attempt used `git checkout <branch> -- dge/data` intending to pull in just one import's new file — that checks out the *entire* directory from that branch's older snapshot, silently reverting every previously-applied import back to its pre-ingest empty state. Caught immediately by re-checking item counts against what each source branch actually produced, and corrected with explicit per-file checkouts instead. No content was lost or shipped wrong; it added an extra fix-forward commit (`cba9204`) to the history.
- **Merge mechanics**: several PRs (parashara/yajnavalkya smriti, shishupalavadha, ramayana, bhagavata, mahabharata, kumarasambhava, kiratarjuniya) were applied directly to `main` via targeted file checkouts rather than GitHub's own merge button, for the cascading-conflict reason above — each closed with a comment pointing at the commit that actually carries its content, so the PR history stays traceable even though the merge button was bypassed.

## Repo size / restructuring proposal
GitHub's practical ceiling is roughly ~1 GB before a repo becomes unwieldy (clone time, CI, the web UI), with a hard 100 MB per-file limit without Git LFS. Current state and trajectory:

| Component | Size | Repo today |
|---|---|---|
| Everything currently on `main` (`dge/`) | ~115 MB on disk | ✅ in |
| Kosha, full dataset (once ingested) | ~436 MB | not yet — sample (~63 MB) is in |
| Sarvamoola + search index (pending branch) | ~59 MB (search index alone) | not yet — separate branch |
| **Projected total once everything lands** | **~610 MB** | — |

Still under 1 GB, but growing, and every one of these large pieces is **explicitly flagged by its own build docs as a regenerable build product**, not hand-maintained source — the Kosha dataset is generated from `dict.zip`, and the search index is generated from `build_search_index.py`. That's exactly the kind of content that benefits from living separately from the code + curated text that actually needs day-to-day editing.

**Proposal:** keep `bhumandala` focused on app code + curated grantha text (Vedas, Sarvamoola, Ashtadhyayi, Tirtha, Guru Parampara — all comfortably small, tens of MB at most). Move the two large, regenerable datasets — the full Kosha dataset and the search index shards — into a **separate data repo** (e.g. `bhumandala-data` or similar), fetched by the main site's JS via a plain cross-origin `fetch()` (GitHub Pages serves any public repo's raw files with CORS-friendly headers) or `raw.githubusercontent.com`. This keeps the main repo's clone/CI/history fast indefinitely, and either dataset can independently grow toward its own multi-GB ceiling without threatening the other. **This needs the project lead's decision before executing** — creating a new repo and moving data across is a real structural change, not something to do silently.

### Convert tool (`dge/convert/`, now v0.15.0)
PDF/page-images/URL → Vision OCR → Gemini proofread → Schema Mapper → GitHub push, all resumable via IndexedDB.

**OCR-verification-guidance implementation (9 Aug 2026), Phases 1-4 of the project lead's spec doc:**
- **Phase 1 — foundational evidence capture**: `vision.js` and `tesseract-check.js` now both return per-word `{text, confidence, boundingBox}` arrays (Vision's polygon vertices and Tesseract's `bbox` both normalized to the same `{x,y,width,height}` shape), and each OCR'd page now stores its own source image (`masterImage`, base64 PNG) in IndexedDB alongside the text. This is what makes an actual visual review possible later, instead of reviewing bare text against nothing.
- **Phase 2 — comparison before correction**: when the Tesseract cross-check is on, both engines' readings are now sent to Gemini together (`[Vision]` / `[Tesseract]` labeled blocks per page) with explicit instructions to prefer agreement and use judgement on disagreement — replacing the old flow where only Vision's text went to Gemini and Tesseract's reading was shown to a human but never used in the actual correction step.
- **Phase 3 — composite uncertainty score**: Gemini now self-reports a `classification` (`accept`/`review`/`unresolved`) and a `page` number per shloka; `review-classifier.js` combines that with the page's Vision confidence and cross-check similarity into a 5-class score (A=confident+agreeing, B=confident but single-source or otherwise unverified, C=AI-resolved disagreement, D=weakly-resolved disagreement, E=unresolved) — a deterministic function, not another AI call.
- **Phase 4 — human review UI**: new "4. Review Flagged Units" panel — a queue of just the C/D/E units (C optional via checkbox), each showing the source page image with low-confidence words outlined in red, every OCR candidate's full-page text side by side, and Accept/Edit/Mark-unresolved actions that record `humanReviewed` directly on the shloka. `buildSchemaPreview()` now warns (with an option to proceed anyway) if any flagged unit still has no human decision, mirroring the existing missing-pages gate.
- **Bug found and fixed**: `mapper.js`'s `buildGranthaJson()` was keying the output `shlokas{}` object by Gemini's own printed `number` field, which Gemini restarts from scratch in every chunk (documented, expected behavior for multi-chunk books) — so any two shlokas from different chunks sharing the same number silently overwrote each other, losing data, with no error or warning anywhere. Fixed by keying on the merge-safe, book-wide-sequential `index` field instead (assigned once per shloka at merge time, gapless 1..N) — which is also exactly the plain-integer key shape the main reader app already assumes everywhere (see `dge/js/core.js`'s shape note). Confirmed via a real multi-chunk Playwright test: before the fix, 2 shlokas from 2 chunks (both numbered "1" by Gemini) collapsed to 1 in the schema preview; after, both survive. **This predates today's work and is independent of Phases 1-4 — anyone who has already pushed a multi-chunk book through Convert should double check nothing was silently dropped.**
- Deferred, not attempted this session: Phase 5 (GitHub Actions automation of this pipeline — needs a decision on where automation credentials would live, since all keys are currently BYOK/client-side only).
- **Phase 6 (Lipi Gnani) — researched, not implemented; no clear integration path found.** Lipi Gnani is a real, published Kannada-script OCR from IISc (H.R. Shiva Kumar / A.G. Ramakrishnan, ACM TALLIP 2020) that measurably beats Tesseract on Kannada-script Sanskrit — 8-8.5% higher word accuracy per the paper. But it's an academic research system, not a public product: no public API, no downloadable package, no stated open licence turned up in a search of the paper, IISc's eprints listing, and IISc's own site. It's since been commercialized by a separate startup (BhaShiNi Digitization Services, for e-book digitization), which if anything makes a free/self-hosted integration less likely, not more. Given DGE's no-backend, BYOK, client-side-only architecture, integrating it would need either a public HTTP API (none found) or a locally-runnable model DGE could ship/call (none found either). Matches the spec doc's own caution not to make this mandatory until feasibility is verified — verified now, and it isn't feasible with what's publicly available. Worth revisiting only if the project lead has a direct research contact at IISc or finds a released model/API this search missed.

Recent additions (8 Aug 2026 and earlier):
- Super-admin-only page selection (`1-10, 15, 20-25`) scoping both OCR and Proofread to the same pages, defaulting to all.
- Gemini model override (fixes hitting a rate-limited default model).
- Missing-page tracking with a "risky, proceed anyway?" confirmation before building a schema with gaps.
- Copy-log button.
- Auto-retry with backoff (3 extra attempts, 5s/15s/45s) on transient OCR/Proofread failures before requiring manual intervention.
- Screen Wake Lock during active runs (stops the phone screen auto-locking mid-run — the most common everyday cause of a run getting backgrounded; switching apps entirely is a hard mobile-browser platform limit no page code can override).
- `navigator.storage.persist()` requested on load, to reduce the chance of the browser silently evicting saved progress under storage pressure.
- A "files with saved progress on this device" hint panel.
- **OCR accuracy tooling**: switched Vision's feature type from `TEXT_DETECTION` to `DOCUMENT_TEXT_DETECTION` (Google's own recommendation for dense document/book pages, not sparse scene text — was using the wrong one); added an optional language-hints field (e.g. `kn` or `kn,sa` for Sanskrit-in-Kannada-script pages, which auto-detect can otherwise misjudge); the raw OCR preview now shows Vision's own per-word confidence per page and highlights specific low-confidence words, so a human review pass can target exactly what's worth checking instead of re-reading every page. This is a real signal, not a substitute for verification against the source — there's still no way to check OCR against ground truth with zero human involvement, since none exists for an unseen scan.
- **Free independent second-opinion OCR** (opt-in checkbox): Tesseract.js (WASM, runs entirely in-browser, no new API key) runs alongside Vision on request, and the preview shows a character-level similarity score plus a word-level diff between the two engines' output. Agreement between two independent engines is a stronger signal than either one's own confidence score. Off by default — roughly doubles per-page OCR time and downloads a language model on first use. Verified with a real (not mocked) Tesseract.js run: real WASM engine, real language data, correctly read a test image and correctly flagged a deliberate mismatch at the right similarity score.
